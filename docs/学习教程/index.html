LESSON 01

LESSON 04

04｜用户注册与登录

注册入口在 UserController.register，它调用 UserServiceImpl.createUser。该服务检查用户名、邮箱，写入用户及分组关联，再创建用户名密码身份；该方法带有 @Transactional。

→

→

→

登录方法按用户名查找用户，调用 UserIdentityServiceImpl.verifyUsernamePassword 校验密码，再调用 DoubleJWT.generateTokens。JWT 的具体签发和权限拦截细节由外部 Lin CMS 依赖参与，需结合依赖源码与运行环境核实。

代码中的 LocalUser 使用 ThreadLocal，而登录方法也把用户写入 SingleUtil.userDO 静态字段。两者的生命周期不同：静态字段由进程共享。不要仅凭类名就认定整个请求链路的用户上下文都安全。
练习：为什么注册时需要事务？

一次注册涉及用户、分组关系和身份信息等多次写入。事务让这些写入在异常情况下有机会作为整体回滚；实际回滚效果仍应通过运行和数据库状态验证。

LESSON 05

05｜职位发布和查询

从 PositionController.create 开始。它接收并校验 CreateOrUpdatePositionDTO，调用 PositionServiceImpl.createPosition，服务将字段赋给 PositionDO 并插入数据库。更新职位的方法将状态设为 0，代码注释解释为需要重新审核。

查询路径可读 PositionMapper.xml：详情查询关联职位、公司和分类；关键词查询使用 LIKE；热门职位按浏览量排序。职位详情页加载时调用浏览量更新接口。关注发布通知的逻辑在第 8 章。

练习：为什么更新职位后状态要变为 0？

当前代码体现的规则是内容更新后重新审核。进一步应该核实：谁有权审核、状态值具体含义、更新和通知是否需要事务。

LESSON 08

08｜关注、通知与 WebSocket

FollowController.addFollow 写入关注记录，还使用反射和全局 map 建立观察者关系；职位发布时 PositionController.create 调用观察者通知并将 map 中的消息写入通知表。静态 map 的数据在进程内，重启与并发情况下的表现需要专门验证。

WebsocketConfiguration 根据配置决定是否启用 WebSocket；WsHandlerImpl 保存连接并提供发送方法。代码中有 WebSocket 组件，不等于前述职位通知或面试通知已经通过 WebSocket 实时送达。追踪调用方、配置和页面行为才能确认。

练习：数据库通知与 WebSocket 有什么区别？

通知表保存记录，WebSocket 是连接与实时传输机制；能否关联起来取决于实际调用代码和运行配置。

LESSON 10

10｜接手开发时怎么排查

现象按顺序查
按钮点击没反应查看浏览器控制台 → 页面方法是否触发 → Network 中是否发请求 → 请求是否报错。
接口失败记录请求方法、路径和参数 → 查看响应 → 搜索 Controller → 查看后端日志、参数校验和权限。
列表数据不对对照查询参数 → Service 与 Mapper 参数 → SQL 的 WHERE/JOIN → 数据库真实记录。
数据更新不完整列出所有写操作 → 确认事务入口 → 检查异常和返回值 → 在隔离环境验证回滚。

准备改功能时，先记下预期行为，定位调用链和关联表，再设计最小改动。改完应验证正常、无数据、无权限、重复操作等情况，并把验证结果和未验证项记录下来。

示例练习：为“同一用户重复投递同一职位”设计约束。先明确撤销后是否允许再次投递、软删除如何处理，再设计数据库约束和服务端错误返回，最后验证并发提交。设计要结合产品规则，不直接把某一种索引写法当成唯一答案。
